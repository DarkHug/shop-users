# prosto_shop — фронтенд для ручной проверки авторизации

Небольшое SPA на Vite + React + TypeScript поверх FastAPI-бэкенда из `src/`.
Нужно, чтобы руками прогонять сценарии авторизации в браузере: регистрация,
вход по паролю, вход через Google/GitHub, обновление и ротация токенов, выход.

## Требования

- Node.js 20+ (проверялось на 25.2)
- запущенный бэкенд на http://localhost:8000 (вместе с Postgres и Redis)

## Установка и запуск

```bash
cd frontend
npm install
cp .env.example .env     # при дефолтном адресе бэкенда можно не создавать
npm run dev              # http://localhost:3000
```

Другие команды:

```bash
npm run typecheck   # tsc --noEmit
npm run build       # typecheck + production-сборка в dist/
npm run preview     # посмотреть production-сборку, тоже на порту 3000
```

## Переменные окружения

| Переменная      | По умолчанию             | Назначение                                |
| --------------- | ------------------------ | ----------------------------------------- |
| `VITE_API_URL`  | `http://localhost:8000`  | базовый адрес API, без слеша на конце      |

Переменные читаются Vite только на старте — после правки `.env` dev-сервер нужно
перезапустить. Файл `.env` в git не попадает (см. `.gitignore`), в репозитории
лежит только `.env.example`.

## Порт 3000 зафиксирован

В `vite.config.ts` стоит `port: 3000` и `strictPort: true`. Порт менять нельзя:

- `http://localhost:3000/auth/<provider>/callback` зарегистрирован как redirect_uri
  у провайдеров;
- CORS на бэкенде (`src/app.py`) разрешает единственный origin `http://localhost:3000`.

`strictPort` не даёт Vite молча переехать на 3001, если 3000 занят — вместо
непонятных CORS-ошибок будет честное падение при старте.

## Страницы

| Маршрут                   | Что делает                                                        |
| ------------------------- | ----------------------------------------------------------------- |
| `/`                       | редирект на `/me` при наличии токенов, иначе на `/login`           |
| `/login`                  | вход по email + паролю, кнопки Google и GitHub, ссылка на регистрацию |
| `/register`               | регистрация; после успеха — `/login` с сообщением                  |
| `/auth/google/callback`   | обработка возврата от Google                                       |
| `/auth/github/callback`   | обработка возврата от GitHub                                       |
| `/me`                     | защищённая страница: `GET /users/me`, выход, ручное обновление токенов |

## Как устроен код

```
src/
  api/
    client.ts     обёртка над fetch: Authorization, разбор ошибок,
                  single-flight обновление токенов и один повтор запроса на 401
    auth.ts       функции конкретных эндпоинтов + типы ответов
    errors.ts     ApiError и разбор detail (строка либо массив 422)
  auth/
    tokens.ts     чтение/запись пары токенов в localStorage
    oauth.ts      state: вытащить из ссылки, сохранить в sessionStorage, забрать
  components/     Alert, Field, ProviderButtons, RequireAuth
  pages/          LoginPage, RegisterPage, OAuthCallbackPage, MePage
```

Три места, где логика неочевидна, и почему она такая:

- **Обновление токенов строго single-flight.** На бэкенде ротация refresh-токенов
  с детекцией повторного использования: два параллельных запроса с одним и тем же
  refresh будут приняты за кражу токена, и бэкенд отзовёт все сессии пользователя
  (`revoke_all_for_user`). Поэтому обновление в любой момент идёт ровно одно,
  остальные запросы ждут тот же Promise. Запрос, стартовавший до обновления,
  повторяется с новым токеном и свою ротацию не запускает.
- **Проверка `state` на странице callback.** Бэкенд не отдаёт `state` отдельным
  полем — он внутри ссылки из `GET /auth/<provider>/url`, откуда его и достаёт
  фронт (`new URL(...)`), сохраняя в `sessionStorage` под ключом провайдера.
  Если `state` из ответа провайдера не совпал с сохранённым или сохранённого нет,
  запрос на бэкенд **не отправляется вообще** — это защита от login CSRF.
- **Ровно один POST на callback.** В dev-режиме StrictMode прогоняет эффекты
  дважды, а `state` на бэкенде одноразовый (Redis `GETDEL`): второй запрос получил
  бы 400 и затёр уже успешный вход. Защита — флаг в `useRef`, StrictMode при этом
  остаётся включённым.

## Хранение токенов

`access_token` и `refresh_token` лежат в `localStorage` (`src/auth/tokens.ts`).
Это сознательное упрощение учебного проекта: токены видны в DevTools, и сценарии
удобно прогонять руками. Минус — `localStorage` читается любым JS на странице,
поэтому при XSS утекает вся пара, включая долгоживущий refresh. В продакшене
безопаснее BFF: токены хранятся на сервере-посреднике, в браузер уходит только
httpOnly + Secure + SameSite cookie плюс CSRF-защита на мутациях.

## Что проверять руками

1. Регистрация с заведомо плохим паролем → читаемый текст ошибки валидации (422).
2. Регистрация на занятый email → «Email already exists» (409).
3. Вход с неверным паролем → «Invalid credentials» (401).
4. Вход по паролю → `/me` с данными пользователя.
5. Кнопка «Обновить токены» на `/me` → в панели внизу меняется пара токенов.
6. Подмена `access_token` в localStorage на мусор + «Повторить /users/me» →
   прозрачное обновление токенов и успешный повтор запроса.
7. Подмена `refresh_token` на мусор, затем то же самое → редирект на `/login`
   с сообщением об истёкшей сессии и пустой localStorage.
8. Вход через Google, в том числе отмена на стороне Google (`?error=access_denied`).
9. Ручная порча `state`: открыть `/auth/google/callback?code=x&state=подделка` →
   ошибка про несовпадение `state`, запроса на бэкенд в Network нет.
10. Кнопка GitHub → «GitHub-вход пока недоступен» (роутер ещё не подключён).

## Известные расхождения с бэкендом

Актуально на момент написания фронта:

- роутер GitHub-провайдера не подключён в `src/routes/__init__.py`, поэтому
  `/auth/github/url` отвечает 404 — фронт показывает «GitHub-вход пока недоступен»;
- `GOOGLE_OAUTH__REDIRECT_URI` в `.env` указывает на `http://localhost:8000/callback`,
  то есть на бэкенд, где такого маршрута нет. Для входа через Google его нужно
  поменять на `http://localhost:3000/auth/google/callback` (и там же, в консоли
  Google Cloud);
- `GET /users/me` для пользователя, созданного через OAuth, упадёт с 500:
  в БД `username` nullable, а в `UserReadDTO` он объявлен обязательным `str`.
